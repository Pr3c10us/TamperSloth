# Visual guidance

Enable the `guidance` tool group to expose `annotatePage` and `waitForUserAction`. Requests such as “guide me” or “step by step” enable it automatically.

`annotatePage` supports arrows, highlights, rectangles, ellipses, corner brackets, freehand paths, and labels. Use a unique observed CSS selector to follow page layout and scrolling, or supply viewport CSS coordinates in `box` / `points`. Labels support an explicit `labelPosition`. Four brand-compatible colors, dashed strokes, line widths, stable IDs, and optional expiration support layered instructions. Remove individual marks by ID or clear the layer. Labels are rendered as text, never HTML. The layer uses an isolated closed shadow root, a cream outline, and pointer-events:none. Motion respects prefers-reduced-motion. There is a limit of 30 simultaneous annotations and 500 path points.

Shapes have a hand-drawn treatment: two subtly irregular curved strokes with round joins, sketch ellipses and arrows, and light clipped diagonal hatching for highlights. Randomness is seeded by annotation ID, keeping the same sketch stable through rendering and scrolling. Target positions and arrow endpoints remain accurate; roughness affects stroke control points. The treatment uses native SVG paths without a drawing-library dependency.

Dashed edges are drawn as separate curved pencil strokes with varied lengths, gaps, and slight endpoint offsets. Dashed ellipses use an irregular dash pattern along a sketch curve. Highlight hatching also uses curved strokes with uneven spacing, clipped to the closed outline. The preview includes **Dashed outline** and **Dashed highlight** buttons.

On-page tips should use 3–8 action-first words, with detailed explanations in chat. The renderer caps visible tips at 90 characters while preserving the full accessible label. Placement measures wrapped text, checks all marked targets, and favors areas clear of nearby controls and other guidance. Explicit positions are preferences; they cannot cover a marked target. Labels reposition on scroll, resize, and layout changes, and hide if no safe position exists.

Guidance uses the extension's bundled Geist and Instrument Serif fonts. Tips match its ink/paper tooltips with 6px corners; cursor badges use cream surfaces, sand borders, and editorial serif text. The cursor badge includes the existing Sloth favicon. These local font and icon assets are declared as web-accessible resources so website styles and fonts do not determine guidance appearance. Waiting and feedback are shown in chat, with screen-reader announcements on the page; there is no on-page waiting popup.

Target tips only use adjacent positions, with at most a 32px gap. They never move to an unrelated viewport corner; if there is no nearby space, the tip hides and the instruction remains in chat. Tips take placement priority over status cards. Starting a wait draws its instruction atomically and clears old annotations; pass `annotationIds` to retain a deliberate canvas region or path. Retained drawings belong to that step and disappear immediately on its expected action. Use `pointerup` for drawing/dragging. Actions captured after a selector annotation appears but before its wait begins are recognized, so the user does not have to repeat the action. Successful completion removes the on-page guidance without showing another completion tooltip.

For each walkthrough step:

1. Inspect the page and identify a unique selector.
2. Call `waitForUserAction` with one instruction, selector, and event (`click`, `change`, `input`, `submit`, or `focusin`). For form completion prefer `change` over `input`, which completes on the first keystroke. Field values are never collected.
3. Where success requires a resulting change, include `expectedSelector` and `expectedState` (`visible`, `absent`, or `checked`). `event:state` waits directly for that condition, including troubleshooting/loading tasks.
4. Inspect the returned status and the current DOM/screenshot before proceeding. A click is evidence of an action, not proof of a successful operation.
5. Clear annotations at the end.

For resumable steps, supply `completion: {selector, state}` with a real success condition (`visible`, `absent`, `checked`, `selected`, or `pressed`). It is inspected before resolving the action target, so an already-selected tool or already-visible confirmation skips a completed step even when its old button selector is gone. Avoid using mere button visibility as proof of completion. Completed guidance receipts retain instructions and completion conditions in the run's compacted task state.

When starting or polling an observer fails, or it reports a lost context/timeout, the tool returns `needsReview` with a fresh accessibility snapshot, screenshot when available, and current page metadata. The agent compares this evidence against completed steps and resumes visual guidance at the first unfinished step with fresh selectors. It does not assume annotations are unsupported because a wait failed. Canvas progress requires screenshot inspection. Explicit cancellation is respected and does not trigger recovery. Recovery instructions limit attempts without new evidence to two before asking the user how to proceed.

Only trusted user events satisfy action steps. Keyboard activation produces ordinary trusted click/change events. Wrong clicks increment a bounded counter without storing their targets or text and show a reminder. Escape cancels without preventing the page's own keyboard handling. Chat Stop sends cancellation too. Timeout defaults to 60 seconds, with a maximum of 120 seconds; results distinguish missing actions from missing resulting changes. The tool has a separate deadline in case page timers stop advancing. Polling uses short messages rather than keeping a service-worker request pending for the entire wait.

Navigation destroys the observation context and returns `lost`; re-inspect the new page rather than assuming the original action succeeded. Replacing a step cancels its listeners and timers. Guidance selectors support the main document and open shadow roots; closed roots and cross-origin frame targets need separate page inspection and cannot currently be anchored by this guidance API. Restricted Chrome pages return an error rather than a successful annotation.

Trusted CDP mouse, keyboard, text, touch, and drag events update the branded cursor before input is dispatched. Once shown, the cursor stays visible at its last position during pauses within a run. Run completion, failure, cancellation, or closing the last extension panel disposes the cursor and annotations on all visited tabs and releases their debugger sessions. The panel's runtime connection provides close detection, and session storage retains visited-tab IDs across worker suspension. Keyboard actions with no focused control preserve the last cursor position instead of moving to the document edge. Click ripples and typing/scroll/drag cues expire; the badge returns to “Sloth” after inactivity. Keyboard input briefly marks the focused control. Legacy click/type/select/scroll/submit tools also show a cue. Decoration failures never block input. No input contents are included in cursor messages or labels.

Run `npm test` for the regression suite, and `npm run build` to package the extension. With Vite running, open `/tests/fixtures/guidance-preview.html` for a manual visual and keyboard fixture. It exercises the actual injected renderer, drawing variants, wrong clicks, Save followed by a visible confirmation, Escape, and timeout.
